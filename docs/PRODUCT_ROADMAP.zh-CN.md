# Sync Tunnel 产品路线图

> 状态：0.2–0.5 规划内容已经合并实现为 `1.0.0-rc.1`；当前门槛是人工多平台验收和 RC 灰度。1.0 前不维护任何旧协议兼容，最终实现以[1.0 架构](ARCHITECTURE_1.0.zh-CN.md)、[1.0 协议](PROTOCOL_1.0.zh-CN.md)和[人工验收](MANUAL_ACCEPTANCE_1.0.zh-CN.md)为准。下方 0.x 小节仅保留路线历史。

## 1. 产品定义

Sync Tunnel 1.0 面向单个自托管管理员，提供多 Vault、多设备的 Obsidian 文件同步。客户端覆盖 Windows、macOS、Android 和 iOS；服务端优先支持 Windows Docker Desktop，并保持标准 OCI 容器兼容性。

1.0 的目标不是多人协作文档系统，也不是公开注册的多租户云盘。同步服务负责可靠复制和版本恢复，但不能替代独立备份。

## 2. 已确认的产品决策

| 主题 | 决策 |
|---|---|
| 用户模型 | 1.0 为单用户、多 Vault、多设备 |
| 默认同步范围 | 默认采用“推荐安全模式”；完整 Vault 同步必须由用户主动选择 |
| 加密边界 | 1.0 使用 HTTPS/Tunnel 保护传输，服务端明文存储；2.0 再实现端到端加密 |
| 客户端范围 | Windows 和移动端属于 1.0 验收范围；macOS 同时保持兼容 |
| 边缘访问 | Cloudflare Tunnel 是推荐入口，Cloudflare Access 是推荐的第二层认证 |
| 项目名称 | 延续 `Sync Tunnel`；正式 Logo 在 0.5 阶段确定 |
| 文档语言 | 中文为当前主文档，0.9 前提供等价英文文档 |
| 漏洞报告 | 先使用 GitHub Private Vulnerability Reporting；公开安全邮箱在 0.9 前补充 |
| 客户端遥测 | 不加入客户端遥测；仅提供本地、脱敏的诊断导出 |

## 3. 产品原则

1. 数据安全优先于速度。任何无法自动合并的内容都必须保留原始字节。
2. 首次同步、大量删除、身份变化和状态丢失不能静默执行破坏性操作。
3. 客户端本地索引可以丢失，但服务端快照必须允许安全重建。
4. 同步状态必须可解释：用户能看到正在做什么、失败在哪里、如何恢复。
5. 默认配置不复制明显的设备状态、缓存、日志或本插件自身文件。
6. 协议、数据库和加密格式都必须带版本，并有明确迁移路径。
7. 历史版本不等于备份；正式发布必须同时验证备份和恢复。

## 4. 同步配置

### 笔记模式

同步 Markdown、Canvas、Bases 和用户选择的附件目录，不同步 `.obsidian`。

### 推荐安全模式（默认）

同步笔记、附件、主题、CSS snippets 和经过审核的 Obsidian 配置。默认排除工作区状态、缓存、日志、临时文件、设备本地状态和 Sync Tunnel 自身插件目录。

### 完整 Vault 模式

同步整个 Vault，包括其他社区插件及其配置。启用前必须提示：其他插件的 `data.json` 可能保存明文 API Key、Cookie 或设备相关路径。

### 自定义模式

按类别和 glob 配置同步范围，并提供匹配预览。排除规则变化时强制执行远端快照对账，不能只继续使用旧游标。

## 5. 版本路线

### 0.2 安全基础

- 为同步状态机建立客户端自动测试和 Fake DataAdapter；
- 增加协议能力发现和 Vault 当前状态快照；
- 客户端状态丢失或排除规则改变时可以安全重建；
- 首次同步支持预览和明确的上传、下载、合并方向；
- 保护 Sync Tunnel 当前及旧版插件目录，禁止其自身程序和设备状态参与同步；
- 检测路径大小写、Unicode 和跨平台兼容问题；
- 引入数据库 schema version 和迁移框架。

发布门槛：多客户端随机状态机测试收敛；本地状态删除后可重建；首次同步不会在未经确认时执行批量删除。

### 0.3 性能协议

实现设计与当前进度见 [0.3 性能协议实施方案](PERFORMANCE_PROTOCOL_0.3.zh-CN.md)。

- 文件事件队列、mtime/size 缓存和周期性校验扫描；
- 持久化 outbox/inbox；
- 临时写入、哈希校验和原子替换；
- 固定大小分块、缺块查询、有限并发和断点续传；
- SQLite 保存元数据，内容寻址 Chunk 保存到 `/data/blobs`；
- 重命名操作和批量提交。

发布门槛：未变化同步不读取文件正文；中断后不重复上传已确认 Chunk；客户端下载内存受并发 Chunk 数限制。

### 0.4 恢复与权限

- per-Vault Token、权限范围、设备注册和撤销；
- 文件版本浏览、单文件恢复、删除恢复；
- 安全 tombstone 保留和基于设备水位线的 GC；
- 在线一致备份、校验、恢复及保留策略；
- `doctor`、`verify`、`gc`、`backup`、`restore` 管理命令；
- 容量配额、速率限制、磁盘空间保护和审计事件。

发布门槛：自动恢复演练成功；撤销设备不能继续同步；GC dry-run 与执行结果可审计。

### 0.5 产品体验

- 首次配置向导、连接诊断和 Vault 选择；
- Activity View、进度、暂停、取消、重试和历史记录；
- 冲突中心、文本三方比较和人工解决；
- 插件、主题、CSS 更新后的重启提醒；
- 移动端资源限制、自适应 UI、中文和英文界面；
- 脱敏诊断包。

### 0.9 公测

- 至少四周真实多设备灰度；
- Windows、macOS、Android、iOS 兼容矩阵；
- 网络中断、磁盘写满、进程崩溃、长期离线和升级故障注入；
- 非官方插件 Release 的 checksum/SBOM、依赖扫描，以及服务端同名 Tag 本地 Docker 构建指引；
- 中英文安装、升级、回滚、备份和排障文档。

### 1.0 稳定版

- 所有发布门槛通过；
- 明确支持周期和协议兼容范围；
- 稳定和 RC 非官方插件发布通道；
- 服务端只分发源码、Dockerfile 和 Compose，不托管预构建镜像；
- 1.0 不提交 Obsidian 官方社区插件目录。

### 2.0 端到端加密

- 完整威胁模型和独立协议评审；
- Vault 主密钥、设备密钥、恢复密钥和设备撤销；
- 文件内容、路径和敏感元数据的版本化加密格式；
- 仅 Vault 内去重，避免跨 Vault 内容等同性泄漏；
- 明文 Vault 到加密 Vault 的迁移与回滚工具。

## 6. 用户配合检查点

开发会在下列检查点暂停，并提供逐步操作说明：

1. 0.2 人工验收：准备两个测试 Vault、至少两台电脑，并确认首次同步预览结果。
2. 0.4 外部配置：启用 GitHub Private Vulnerability Reporting 和分支保护；Actions 只保留插件 Release 所需权限。
3. 0.4 恢复验收：选择不位于同步服务器电脑上的加密备份目标，执行一次恢复演练。
4. 0.5 移动验收：在至少一台 Android 或 iOS 设备上完成安装、离线修改和冲突测试。
5. 0.9 发布准备：确认正式 Logo、安全联系邮箱、英文文档和非官方插件发布说明。

在到达检查点以前，仓库内代码、测试和文档工作可以继续进行，不要求用户反复手工操作。
