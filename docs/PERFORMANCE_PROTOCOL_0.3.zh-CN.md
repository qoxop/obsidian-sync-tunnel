# 0.3 性能协议实施方案

状态：开发中。0.2 全文件 API 在整个 0.3 阶段保持兼容，现有客户端和服务端可以滚动升级。

## 1. 验收目标

1. 普通无变化同步不读取文件正文，只查询远端变更并复用本地元数据缓存。
2. 文件发生变化后，事件先持久化，再由去重队列触发同步；进程重启不会丢失尚未处理的路径。
3. 网络中断后，已经确认存在的 Chunk 不重复上传。
4. 下载只在内存中保留有限数量的 Chunk，最终文件通过临时路径校验后原子替换。
5. 0.2 全文件客户端在 0.3 服务端上仍可使用；0.3 客户端通过能力协商选择传输方式。

## 2. 分阶段实现

### A. 客户端发现层（已实现于 `main`）

- 监听 Vault 的 create、modify、delete 和 rename 事件；
- 以规范化路径为键持久化去重事件，并在连续编辑停止两秒后触发自动同步；
- 保存 `size + mtime + SHA-256` 扫描缓存；
- 事件路径强制重新计算哈希，防止外部工具保留 mtime 和 size；
- 每小时执行一次完整元数据扫描，发现漏报的创建、删除和重命名；
- 每 24 小时执行一次正文完整校验，发现极少见的元数据未变化内容修改；
- 同步期间再次到达的同路径事件使用单调事件值保留，不会被旧任务错误确认；
- 数据结构升级到客户端 schema v3，旧数据首次运行自动执行安全全扫描。

这里的事件队列负责“发现需要检查的路径”，不是网络操作 outbox。只有完整扫描或明确收到文件事件时才会传播本地删除，避免把未扫描文件误判为删除。

### B. 持久化操作层（进行中）

- 将上传、删除转换为带 UUID `operation_id` 的 outbox 项（已实现；重命名留待 D 阶段）；
- 在任何网络写入前保存 outbox（已实现）；
- 服务端在同一事务内记录操作结果和文件 revision（已实现）；
- 单次客户端请求的网络重试复用相同 `operation_id`，提交成功但响应丢失时返回原结果（已实现）；
- 下载计划进入 inbox，文件安全落盘并更新本地状态后再确认远端游标（已实现于全文件下载路径）。

客户端现在会在重启后查询 outbox 对应的服务端结果：已提交则恢复原 revision；未提交且本地内容仍与 outbox 相符才安全重试；本地内容已经继续变化时放弃旧操作并重新扫描。下载先持久化 inbox，再写入同目录临时文件并复验大小和 SHA-256，最后通过备份交换安装；重启后可以识别已安装目标、已验证临时文件或旧文件备份。

### C. Chunk 传输层

- 默认固定 4 MiB Chunk；最后一块允许更小（已实现）；
- Chunk ID 为小写 SHA-256，服务端按内容寻址保存到 `/data/blobs/chunks`（已实现）；
- 客户端提交文件 Manifest 前查询缺块，最多并发传输少量 Chunk（已实现，默认并发 3）；
- 服务端逐块校验长度和哈希，使用同目录临时文件并原子改名（已实现）；
- Manifest 提交携带 `operation_id`、`base_revision`、文件哈希、大小和修改时间（已实现）；
- 未引用 Chunk 只在宽限期后进入 GC，0.3 不执行激进回收；
- 小文件和不支持该能力的对端继续使用 whole-file-v1（已实现）。

服务端 schema v3 保存 Chunk 和 Manifest 元数据。0.3 迁移期 Manifest 提交还会保留完整文件兼容副本，使 0.2 客户端可以继续通过 whole-file-v1 下载；分块下载稳定并具备迁移/回滚测试后再取消这份冗余。

插件已支持逐块下载、逐块哈希校验和最终整文件复验。Obsidian 通用 `DataAdapter` 暂无二进制追加接口，因此跨桌面和移动端的公共实现仍需在最终写入前分配一份目标大小的缓冲区，但不会同时保留多个完整 HTTP 响应。0.3 验收会测量移动端峰值并设置安全文件上限；桌面流式写入作为后续优化。

### D. 重命名与批量提交

- 同一设备事件窗口内用旧路径哈希和新路径哈希识别高置信重命名；
- 重命名作为单个逻辑操作提交，避免先上传后删除造成短暂重复；
- 批量提交为同一组操作分配连续 revision，并返回逐项结果；
- 无法证明是重命名时仍按上传加删除处理，数据安全优先。

## 3. 本地状态

客户端 schema v3 新增：

| 字段 | 作用 |
|---|---|
| `scanCache` | 保存路径对应的 size、mtime 和 SHA-256 |
| `pendingPaths` | 保存尚未成功完成同步的去重文件事件 |
| `needsFullScan` | 文件夹事件或状态异常时强制完整扫描 |
| `lastFullScanAt` | 控制每小时完整元数据扫描 |
| `lastIntegrityScanAt` | 控制每日正文重新校验 |

客户端 schema v4 加入 `outbox`，schema v5 加入 `inbox` 和临时下载清单。后续 schema 会加入 Chunk 上传确认集合。所有结构都必须通过迁移函数加载，不能直接假设旧版字段存在。

## 4. 服务端存储演进

SQLite 继续保存 Vault、路径、revision、Manifest、operation 和引用关系；大块内容保存在映射到宿主机的 `/data/blobs`。数据库事务只提交已经完成哈希校验并可读取的内容引用。

服务端升级顺序：先部署同时支持 whole-file-v1 与 chunk-upload-v1 的版本，再逐台升级插件。回滚时旧服务端无法处理尚未提交的 Chunk，但已经提交的文件仍必须保留 whole-file 下载兼容路径。

## 5. 测试门禁

- 缓存命中时断言 `readBinary` 调用次数为 0；
- 同一文件事件合并、重启恢复、同步中再次修改；
- 部分扫描只能删除队列明确记录的路径；
- 全扫描发现漏报删除和大小写或 Unicode 冲突；
- 服务端提交后丢失响应，使用相同 operation ID 得到相同 revision；
- 传输中断后只上传缺失 Chunk；
- Chunk 被篡改、截断、重复提交和 Manifest 总大小不匹配；
- 0.2 客户端与 0.3 服务端、0.3 客户端与禁用 Chunk 能力的服务端兼容。

达到全部验收目标并经过双设备真实 Vault 验证后，才发布 0.3.0。
